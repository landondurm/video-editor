# Incremental Graphics — render → lock → composite (second-pass loop)

How the **second pass (step 4)** edits graphics **without re-rendering the whole video** every tweak. Format-agnostic — applies to any HyperFrames graphics build (short or long). Adopted 2026-06-24 on `your-job`.

## The problem it solves

A monolithic HyperFrames render captures every frame of the whole composition — ~3–4 min for a 47s reel, far worse for long-form. Changing one graphic shouldn't pay that cost. With this pattern you re-render **only the part you changed** (seconds) and recomposite (an ffmpeg pass, ~5s). The base footage and every locked graphic are never touched again.

## The architecture

Three layer types, composited by ffmpeg over the **base** (the rough cut — rendered ZERO times by graphics):

| Layer | What | Rendered as | Why |
|-------|------|-------------|-----|
| **base** | the rough cut (`outputs/<job>.mp4`) | already done | never re-rendered |
| **overlay graphic** | a card/panel/caption floating OVER the footage (G1, lower-thirds, callouts, the self-demo pops) | standalone comp → **transparent `.mov`** (`--format mov`) | composite onto base at its timestamp; re-render in isolation |
| **segment** | a part that *modifies the footage itself* — the camera-reframe takeover, a full-screen cutaway, a speed ramp | standalone comp **with its own base slice** → opaque `.mp4` | overlaid opaque, it *replaces* the base for its window |

**Decide overlay vs segment by one question:** does the part change the underlying footage (crop/move/replace the face, full-screen takeover)? → **segment**. Does it just float on top? → **overlay**.

## What the build emits

A parts-oriented `build.py` (single source of truth: CSS + per-graphic markup + per-graphic anim) generates:

```
compositions/<id>.html   one comp per part (transparent overlay, or opaque segment w/ its base slice)
render-part.sh <id>      render ONE part → renders/parts/<id>.{mov|mp4}   (seconds)
render-all.sh            render every part, then assemble
assemble.sh              ONE ffmpeg overlay pass: base + segments + overlays → renders/final.mp4  (~5s)
parts.json               manifest (id, window, kind, comp, clip)
index.html               full monolithic comp (fallback / from-scratch render)
```

Each part comp's GSAP timeline is **rebased to start at 0** (the build subtracts the part's start time); `assemble.sh` places each clip back at its real timestamp with ffmpeg `-itsoffset` + `overlay=enable='between(t,start,end)'`.

## The loop

```
edit build.py  (tweak one graphic's markup/timing)
python3 build.py                # regenerates that part's comp
# PROBE the comp in the browser (below) — a render costs minutes, a probe costs one call
./render-part.sh G4             # re-renders ONLY G4 (~30-50s)
./assemble.sh                   # recomposites the final (~5s)
# review renders/final.mp4 → lock it → next part
```

Lock graphics one at a time. "Render everything together" at the end is just `./assemble.sh` — no full re-render unless the base cut changes.

### ⭐ Probe the comp in the browser BEFORE rendering (2026-08-05, your-job)

Rendering to find out whether a graphic works is the most expensive habit in this pipeline. A part is 1.5–3.5 min; seeking the paused timeline in the Browser pane is one tool call. Open `file://<abs>/compositions/<id>.html` and measure the **mechanics** — element positions, pivots, whether a tween actually fired, whether a part's frame 0 is the settled seam state:

```js
(() => { const t = window.__timelines.main, o = {};
  [8, 24, 50, 80].forEach(f => { t.seek(f * 1001 / 30000);          // fps of THIS job
    const e = document.getElementById('gear1'), b = e.getBoundingClientRect();
    o['f'+f] = [Math.round(b.x + b.width/2), Math.round(b.y + b.height/2), e.getAttribute('transform')];
  }); return o; })()
```

The failures this catches are **invisible in a contact sheet**: a wrongly-pivoted element still animates, it just orbits the frame, so the sheet reads as "odd design" rather than "bug". On `your-job` that cost roughly five render passes. Two traps: **`seek(0)` when the timeline is already at 0 is a no-op** returning the pre-render state (seek away and back), and `location.reload()` inside the probe kills the execution context — re-`navigate` with `force: true`.

**Scope: the probe is for MECHANICS on new or structural work.** On second-pass nudges (move, resize, retime, recolor a locked graphic), skip visual self-QA entirely: edit, render the part, assemble, link the draft with the full repo-root path, and confirm only that the render exited clean. the creator watches the draft and calls the fixes; full visual QA is reserved for first drafts and structural or risky changes.

### ⭐ Let the build tell you which parts are stale — don't remember the coupling rule

Stamp `renders/<id>.sha` with the hash of the comp each render was built from, and add a `--stale` mode that diffs comp-hash vs stamp. Because every part of a chain embeds the **whole shared timeline** in its own HTML, touching one shared element marks *every* part of that chain stale — which is the seam-coupling rule below, enforced instead of remembered. Build the stamp + `--stale` mode into your own `build.py` (no sample project ships). It was written after shipping a part whose tail frames still showed the *previous* version of the neighbouring scene.

## Split long graphics into seamless part clips (LOCKED SOP — you, 2026-07-21)

Render time is **linear in comp duration** and a tweak re-renders the whole comp, so a long multi-scene graphic (the `your-job` g2 grew to 19s ≈ 85s + 1.5 GB per tweak) must ship as **short part clips, butt-joined** — adjacent clips on the Premiere timeline, or adjacent segments in the ffmpeg composite. Split even when scenes flow continuously; split **on a transition** if that's where the cut wants to be — the seam just has to frame-match.

- **Mechanism (frame-match by construction):** keep ONE shared timeline for the whole graphic in `build.py`; emit each part from it with a start offset — `emit("g2", durA, ...)` + `emit("g2b", durB, ..., t0=durA)`. The emit template wraps `tl` in a shim that shifts every position by `−t0` and collapses any set/tween that ends before the seam into its END state at time 0. Part N+1's first frame therefore **is** part N's last frame, pixel-identical, whether the split lands on a hold or mid-transition. (GSAP note: `master.add(tl, -t0)` does NOT work — negative positions get clamped; the shim is the way.)
- **Cut on exact frame counts:** part durations = `k * 1001/24000` (23.976) so clips butt-join on the sequence frame grid with no gap or overlap.
- **Grain is free:** the film-grain flicker alternates every few frames anyway, so the grain-phase flip at a seam is invisible (it also defeats the renderer's static-frame dedup — another reason parts, not monoliths).
- **Premiere side:** each part = its own project item + clip (per-part `refreshMedia`); baked Transform keys (exit pushes) live on the part that plays them.
- **Coupling rule:** the seam frame shows shared content, so a change visible at the seam = re-render BOTH adjacent parts (same build, so it's one `python3 build.py` + two `render.sh` calls). A change contained inside one part = re-render that part only.
- **Motion THROUGH a seam = per-frame sets on FRAME-INTEGER times (the one-frame-stutter trap, 2026-07-21).** A `.to()` that straddles the seam gets clamped by the shim, so emit the move as per-frame `tl.set`s — but compute each set's time as `(frameIndex) * 1001 / 24000 - 0.0005`, NEVER from a rounded decimal base. A decimal like `18.601917` sits ~3e-7 AFTER the sampler's frame time; whether a part's `t0` rounding cancels that error decides which side of the frame sample each set lands on, and the whole move plays one frame late in one part only → a double-step stutter exactly at the seam. The `-0.0005` guard makes every set land safely before its frame sample in both parts. Also: a mid-motion seam CANNOT be verified by diffing part N's last frame vs part N+1's first (they're adjacent frames of real motion, they SHOULD differ — and the renderer samples frame STARTS, so "part N last frame" is one frame-step before the seam state). Verify by measuring the moving element's position across the 4 frames spanning the join: the per-frame steps must follow the easing curve smoothly.

No sample project ships: the bullets above are the complete spec for the emit-`t0` shim and the straddling-motion pattern.

## Gotchas (learned, don't relearn)

- **Pin the CLI version in every render script.** A bare `npx hyperframes` floats to whatever shipped last (the 0.7.42 contract break landed mid-job exactly this way). `build.py` must emit `npx hyperframes@<tested version>` (currently `0.7.92` for new jobs — validated 2026-08-04 by a one-part A/B vs `0.7.68`: the `--format png-sequence` frames are bit-identical 84/84, so the renderer is unchanged and only the h264 encode differs, at 46 dB PSNR; never `0.7.67`, RenderStretch landed there and was reverted). Jobs already rendering on an older pin keep it. Bump the pin deliberately: edit it, re-render one part, review, then adopt.
- **Glass/panels must be opaque-bright.** A transparent overlay render has nothing behind it, so `backdrop-filter` blur of the footage does NOT happen in isolation. Design panels to read on their own fill (frosted-bright), not on live backdrop blur — then the overlay composites identically to a same-pass render. (We'd already moved to bright glass for contrast; this makes it free.)
- **Match fps to the base.** Render every part at the base's frame rate (`--fps 24000/1001` for 23.976 footage) so overlays/segments stay frame-aligned through ffmpeg. Mixed fps drifts.
- **Segments carry their own base slice.** Cut the footage window once (`ffmpeg -ss A -to B`) into `assets/<id>-base.mp4`; the segment comp uses THAT as its `#head`/`#head2` so its first/last frame matches the base at the seam → seamless overlay.
- **Cut the slice at the PLACED time, not the build time (the stutter/desync trap).** If the base was re-spliced and graphics slide via a `PLACE_SHIFT` (e.g. a lead-in added downstream), a segment's slice must be cut at `build_time + shift` — the spot where it's actually overlaid — NOT the raw build time. Cut it at the build time and the segment's footage **jumps** at the seam (a visible stutter) and runs **out of sync** with the base audio for its whole duration (the segment plays footage from the wrong moment). Overlays just slide (no footage, no problem); only segments carry footage, so a base re-splice means **re-cut the slice at the placed time AND re-render the segment**. Verify: the slice's frame 0 luma should match `ffmpeg -ss <placed_start> -i base` (same frame → aligned).
- **Render parts at `-q standard`** so `renders/final.mp4` is already final quality — the assemble is the deliverable, no separate "final render" step.
- ⭐ **A browser segment reframes via the WRAPPER's layout box — never GSAP-`transform` the `<video>` itself (it silently drops from the render).** Put a `transform`/`scale`/`x`/`y` on a `<video>` element and HyperFrames' headless render quietly composites it away — the face just **vanishes** where the move should be, no error, no lint. (Same wall the vendored faceless-explainer/pr-to-video pipelines hit: their hoisted `<video>` *"cannot follow in-scene GSAP transforms"*, so its slot must hold STILL.) The shipped takeover dodges it by reframing through **layout, not transform**: the `<video id="head">` (`width:100%;height:100%;object-fit:cover`) sits inside a `<div id="headwrap">` with `overflow:hidden`, and GSAP animates the WRAPPER's `left/top/width/height` (+ `borderRadius`/`boxShadow`) from full-frame `(0,0,1920,1080)` to the 4:5 card `(1124,150,624,780)` — the parent shrinks/slides and crops the still-untransformed video. So full-screen cutaways and face-reframe takeovers work as browser segments **only** via wrapper-box layout animation. **Prefer not needing it at all:** a pure scale/move/push-in PiP is cleaner as an `ffseg` (ffmpeg `zoompan` — zero browser round-trip, zero brightness dip) or a transparent-overlay move; reach for the browser segment only when the reframe needs live graphics revealing *behind* the moving face.
- **The segment brightness-dip trap — fix it at the ROOT, not afterward.** A browser "segment" round-trips its footage through the HyperFrames headless browser (decode→RGB→re-encode), which **darkens the face ~3%** (YAVG ~2.8 on a 16–235 scale) vs the passthrough base. So the face visibly dims at every segment seam. Overlays never show it (translucent graphics, no adjacent base to seam against) — only footage segments do. Two root causes stack, address in this order:
  1. **Do footage motion in ffmpeg, not the browser — `ffseg` kind.** A zoom/push-in/pan is pure YUV geometry; render it with ffmpeg `zoompan` on the base slice and it NEVER enters the browser → **zero shift** (measured 92.42 vs base 92.38). The associated graphic (chip/callout) stays a separate transparent overlay composited on top. This is the real fix — prefer it whenever the footage move is expressible in ffmpeg. `zoompan` gotchas: `crop` w/h can't animate (only x/y are per-frame — `t` is undefined when w/h are configured, errors `-22`); upscale 2× first (`scale=3840:2160`) so the zoom doesn't quantization-jitter; ease on output time `on/fps` with a cosine so zoom=1.0 at both seams; set `fps=` to the base or frames drift.
  2. **If it MUST be a browser segment (complex animated reframe — rounded card, border, revealing graphics behind — that ffmpeg can't sanely do): extract source frames as PNG.** Add `--video-frame-format png` to the segment's render (HF default `auto` extracts to lossy JPG, which is most of the dip) — that alone roughly halves it (~2.8→~1.2). Close the small remainder with a residual **gamma** lutyuv on that segment in assemble (no re-render): `lutyuv=y='clip(pow(clip((val-16)/219,0,1),1/G)*219+16,16,235)'` — gamma (not a flat gain) pins black & white so highlights don't clip. After PNG, **G≈1.03** landed the takeover within 0.03 luma of base. Re-derive G by comparing frame 0 (scale-1.0, same crop) of the segment render vs its `<id>-base.mp4` slice via `signalstats` `YAVG`, tuning until they match.
- ⭐ **An `ffseg` zoom on a slice that doesn't start at t=0 needs `trim`+`setpts` to reset zoompan's `on`, or the zoom is CONSTANT (looks like a cut, not a ramp).** `zoompan`'s frame counter `on` counts from where its filtergraph input begins. Slice with `-ss <S>` placed AFTER `-i` and ffmpeg still feeds zoompan frames counted from the **video start** — so for a mid-video part (`S>0`) `on` is already huge at frame 0 and an `on`-based ramp (`1+amp/(1+exp((c-on)/w))`, `1+amp*(1-on/N)^2`, a cosine, …) is pinned at its end value the entire clip → a constant zoom that reads as a hard cut. Invisible when the part starts at 0 (the intro zoom works by luck). **Fix:** build the slice with `trim=start=S:end=E,setpts=PTS-STARTPTS,<zoompan…>` in the filtergraph (NOT `-ss S -t DUR`), so zoompan receives only the windowed frames and `on` starts at 0. Verify by eye: the slice's frame 0 must match the base at `S` (scale 1.0), later frames visibly zoomed. (`build.py`'s `render-part.sh` ffseg branch now always uses trim+setpts.)
- **Anchor footage motion to the MEASURED cut, not the nominal time.** The rendered base drifts from the nominal cut timeline (`cuts.json`/`segments.tsv`): on `your-job` the segments summed to 46.98s but the real base was 47.38s — ~0.4s accumulated by the end, and the transcript shares that drift. A NOSHIFT `ffseg` zoom placed at the nominal cut therefore lands ~0.3s early and creeps onto the previous clip's tail (you caught the outro zoom starting before the cut). Get the real cut from the *rendered* base: `ffmpeg -i video.mp4 -vf "scdet=threshold=0,metadata=print:file=-" -an -f null -`, then take the peak `scd.score` in the gap (same-framing jump cuts score low, so use `threshold=0` and pick the max, not a fixed threshold). Cut the slice with `-ss <time>` **after** `-i` (decode-accurate; `-ss` before `-i` is keyframe-only and can be off by ~0.5s). The `PLACE_SHIFT=0.30` applied to overlays is an approximate correction for this same drift — but footage `ffseg` parts are NOSHIFT, so anchor them to the measured cut explicitly.
- **To hold a footage zoom to the end (push-in that doesn't zoom back out), use the overlay's `eof_action=repeat` — NOT `tpad`.** `tpad=stop_mode=clone` chained after `zoompan` (with videotoolbox) RUNS AWAY: it never EOFs, ballooned a ~4s clip to 1GB+ before it was killed (same no-EOF family as the `-loop 1` PNG-overlay trap). Instead let the zoompan clip end naturally (it trims ~2 frames off the tail) and set `eof_action=repeat` on that part's `overlay=` in `assemble.sh` — it holds the last held-zoom frame through to the base end, no pop-out. (build.py special-cases `eof_action` for the closing `outroz` part.)
- ⭐ **Every OTHER overlay needs `:eof_action=pass`, or ffmpeg silently duplicates ~1-in-4 output frames (the stutter trap — cost six rounds to find).** `overlay` defaults an ended input to `eof_action=repeat`. Chain ~9 short overlays over the long base, each defaulting to repeat, and the frame scheduler — juggling several ended-but-still-repeating inputs — starts duplicating OUTPUT frames on a periodic cadence (measured **exactly 1 in 4**). The killer: the output is dead-even CFR (23.976), so ffprobe, frame counts, and PTS all read **perfectly fine** — but the content only changes ~18×/sec wearing a 24fps costume → visible judder, worst on smooth motion like a zoom. And every *input* (the zoom clip, the slice, the base) measures clean in isolation; the dup exists ONLY in the assembled output — so you keep "fixing" the zoom, which was never broken. **Fix:** set `:eof_action=pass` on every `overlay=` ("when this input ends, pass the base through untouched" — no repeat, no dup). The single exception is a deliberately-held frame (the outro push-in above) → `repeat`. `build.py` emits `pass` on all parts and `repeat` only on `outroz`, so a hand-edit of `assemble.sh` can't silently drop it. **Detect:** `ffmpeg -i out.mp4 -vf "signalstats,metadata=print:key=lavfi.signalstats.YDIF:file=-" -f null -` and tally `YDIF=0` lines (exact duplicates) — clean ~0–3%, the bug ~25%. `assemble.sh` runs this automatically after every composite and **exits 1 if dups ≥ 8%** (the smoothness guardrail — do not remove it; it's the real "never again"). **Do NOT** mask stutter by forcing CFR (`-r`/`fps=`): the output is already CFR, so that just re-times the duplicates and buries the cause.
- ⭐ **No raw emoji glyphs in a graphic — they HANG the headless render (looks stuck, isn't).** A real emoji (`💤`, `😴`, any Apple Color Emoji codepoint) makes HyperFrames' headless Chrome spin at ~100% CPU trying to load the system color-emoji font, which isn't available/decodable in low-memory render mode — it never errors, never times out, just runs forever. A 5s part that should render in ~7s burned **5+ min of CPU** before being killed; the only new variable vs the parts that rendered fine was the emoji. It's not a perf wall (the same part renders in 7s without the glyph) and it's invisible until you watch CPU time pile up on a tiny clip. **Fix:** don't put emoji codepoints in the markup — fake the look with the embedded brand font (e.g. a "sleeping" 💤 → royal-blue italic **"zzZ"** clusters in Inter, which renders instantly and stays on-brand). If you genuinely need a pictographic glyph, bake it as a pre-rendered PNG/SVG asset and overlay it, never as live text the browser must font-resolve — use [`bake-emoji.py`](bake-emoji.py) (`python3 workflows/bake-emoji.py rocket=🚀 check=✅ --out projects/<job>/hf-graphics/assets/emoji`), which renders Apple Color Emoji via PIL at the one valid sbix strike, then trims + pads to a clean transparent PNG. **Smell test:** a render still going after ~3× the others on the SAME-length part = kill it and check the part for an emoji/exotic glyph before assuming a real hang.
- ⭐ **An exit/transition tween must finish INSIDE its clip's `data-duration`, plus a hard-kill at the next clip's start.** HyperFrames hard-hides a clip the instant its window ends — an exit fade still mid-dissolve at that boundary POPS off screen. Extend the clip's duration to contain the exit, and add `tl.set("#id",{opacity:0}, <next-clip-start>)` as the hard-kill. Lint only catches the missing hard-kill half (`gsap_exit_missing_hard_kill`); the too-short-duration half passes lint and pops in the video.
- ⭐ **A fixed-pivot rotate/scale on an SVG element goes in the SVG `transform` ATTRIBUTE, never GSAP `rotation`/`scale` plus an origin (2026-08-05, your-job).** Write `rotate(deg cx cy)` or `translate/scale/translate` on the attribute (per-frame `gsap.set` of the attribute string is fine). Measured on GSAP 3.14.2: px `transformOrigin` values on SVG are bbox-relative, not user-space; `svgOrigin` displaces the element; and GSAP bakes the origin into the matrix, so a later bare `{rotation:N}` tween silently reverts the pivot to the SVG 0,0. The failure is invisible in a contact sheet (the element still animates, it just orbits), which is exactly what the browser probe above exists to catch: verify pivots by seeking and reading `getBoundingClientRect` centers. Cost a full round of re-renders. HTML elements are unaffected; origin-animate those normally.
- ⭐ **Never pre-position a GSAP-tweened element with a CSS `transform`.** A stylesheet `transform:translateX(-115%)` gets absorbed into GSAP's transform cache, so a later `xPercent`/`x` tween nets the wrong end position. Let GSAP own position entirely — set the initial pose via `tl.set(...)` or from-values; keep `transform` out of the CSS for anything the timeline touches.
- ⭐ **ALL CSS must be INLINE in the comp — a `<link rel="stylesheet">` silently does not load in the headless render (2026-07-18, `premiere-pipeline-test`).** The comp renders with zero error and zero lint: fonts fall back to serif, every class from the linked sheet (glass panels, pills) just vanishes. A shared stylesheet is fine as an authoring reference, but inline its contents into each comp's `<style>` before rendering. Smell test: brand font rendering as Times = your linked CSS never loaded.
- **A timeline `fromTo(...)` whose from-pose changes glyph geometry needs `immediateRender:false` (2026-07-18, word-karaoke caption bar).** GSAP applies a `fromTo` from-pose at timeline BUILD time by default, so every word span sat pre-scaled at 1.16 from t=0 — the grown glyph boxes ate the inter-word margins and the un-revealed text rendered PACKED together ("atthebottomofthescreen"). `immediateRender:false` makes the from-pose apply only when the playhead reaches the tween (still seek-safe inside one paused timeline). Any staggered per-element `fromTo` reveal wants this.
- Benign lint noise — don't "fix" these: `duplicate_media_discovery_risk` (two synced video layers, reused logo) is a **warning**; `missing_local_asset: <id>-base.mp4` clears once `render-part.sh` cuts the slice; `timeline_track_too_dense` is a **warning only** (suggests sub-comps — fine to ship as-is); `missing_three_script` is a **false positive** for `+esm` module imports (WebGL still renders).

## Reference implementation

No sample projects ship — author the harness fresh from the architecture above (`build.py` + per-part comps + `render-part.sh` / `assemble.sh`).

> ⚠️ **Keep the `build.py` source DURABLE — do not leave it only in `/tmp`.** This build was authored in `/tmp/video-editor/<job>/hf-graphics/` and macOS's overnight `/tmp` clear **wiped the entire source** (build.py + comps + render parts) — the finished video survived only because it was already copied to `outputs/`. Going forward, the whole build lives under `projects/<job>/hf-graphics/`: the small source (`build.py`, `render-part.sh`, `assemble.sh`, `parts.json`, `compositions/`) plus the heavy regenerables (`renders/`, `assets/*-base.mp4` slices, font copies) as its cache, rebuilt by `setup-assets.sh` + `render-all.sh` and reclaimed by `prune.sh --apply` once the job ships. Nothing lives solely in `/tmp`.
